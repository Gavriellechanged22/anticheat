# User-mode anti-cheat prototype

Пассивный прототип сенсора для Windows на C/WinAPI. Текущая версия ничего
не записывает в память игры и не завершает её: она собирает наблюдения и пишет
их в JSON Lines. Это намеренное ограничение — сначала нужно измерить ложные
срабатывания на реальных конфигурациях.

## Что не так с исходным планом

1. **Запрошены избыточные права.** Для мониторинга нужны
   `PROCESS_QUERY_INFORMATION | PROCESS_VM_READ`. Права `PROCESS_VM_WRITE` и
   `PROCESS_VM_OPERATION` не нужны, увеличивают последствия компрометации
   античита и могут конфликтовать с другими средствами защиты.
2. **Снимок памяти при старте не является доверенным эталоном.** Чит может
   появиться раньше сенсора. Кроме того, загруженный PE уже отличается от файла
   на диске из-за ASLR-релокаций, импортов, delay-load, hotpatching, DRM и
   легитимного runtime-кода.
3. **Хэш всей `.text` слишком грубый.** Он не показывает место изменения,
   дорого пересчитывается и даёт ложные срабатывания на изменяемых участках.
   Нужны подписанный manifest версии игры, разбор PE и хэши нормализованных
   блоков/секций с явными исключениями.
4. **«Незнакомая DLL = инъекция» неверно.** В игру штатно попадают оверлеи,
   драйверные компоненты GPU, аудио middleware, accessibility-инструменты и
   антивирусы. Имя и путь также легко подделать. Нужна комбинация: SHA-256,
   Authenticode publisher, версия, происхождение загрузки и подписанный
   allowlist. Даже после этого неизвестный модуль сначала является сигналом.
5. **Toolhelp не видит всё и подвержен гонкам.** Список может измениться во
   время снимка; manual-mapped или unlink-модуль может отсутствовать в loader
   list. Нужна корреляция списка модулей с `VirtualQueryEx`/`MEM_IMAGE`, а
   ошибки `ERROR_BAD_LENGTH` следует повторять. Сенсор желательно собирать
   x64, иначе он не сможет корректно перечислять модули x64-игры.
6. **StartAddress потока не предоставляется стабильным документированным
   Win32 API.** Часто используют `NtQueryInformationThread`, но этот контракт
   внутренний и зависит от версии Windows. Кроме того, легитимный стартовый
   адрес не мешает потоку позже перейти в чужой код. Такая проверка годится
   только как дополнительная телеметрия.
7. **Anti-debug проверки описаны неточно.** `IsDebuggerPresent()` проверяет
   вызывающий процесс, то есть отдельный anti-cheat проверит самого себя, а не
   игру. Для цели применим `CheckRemoteDebuggerPresent`, но и он обходится и
   может сработать на легитимной диагностике. Прямое чтение PEB хрупко при
   WOW64 и не должно быть основанием для санкции.
8. **Проверка только первого байта на `0xE9` ненадёжна.** Хук может быть
   выполнен другими инструкциями, а переход может быть легитимным thunk или
   hotpatch. Проверять нужно канонизированный диапазон функции/секции, её
   принадлежность модулю и целевой адрес перехода.
9. **Сканирование всех чужих процессов по памяти — плохая граница
   приватности.** Оно требует дополнительных прав, дорого стоит, вызывает
   конфликты с защитным ПО и всё равно легко обходится переименованием или
   внешним устройством. В первой версии его нет.
10. **`TerminateProcess` — слишком опасная первая реакция.** Возможны потеря
    прогресса, повреждение файлов и наказание невиновного пользователя. Клиент
    должен отправлять доказательства, сервер — оставаться авторитетным, а
    политика реакции должна учитывать несколько независимых сигналов.
11. **Не определены производительность и эксплуатация.** Нужны лимиты CPU/I/O,
    debounce одинаковых событий, ротация логов, защита от утечки персональных
    данных, подпись конфигурации, версия правил, метрики false-positive и
    безопасный rollout.
12. **Ring 3 не создаёт корень доверия.** Процесс с равными или большими
    правами способен остановить или подменить сенсор. Подписанный сервис,
    watchdog и heartbeat повышают стоимость обхода, но не превращают user-mode
    решение в kernel anti-cheat.

## Дополненная архитектура

Поток данных следует строить как:

`сборщик -> нормализация -> независимые сигналы -> корреляция/score -> журнал -> серверная политика`

Рекомендуемые этапы:

1. Сформулировать threat model, поддерживаемые Windows/архитектуры и бюджет
   производительности. Запускать x64-сборку рядом с игрой и валидировать полный
   путь/время создания процесса, а не только имя.
2. Реализовать observe-only инвентаризацию модулей и страниц памяти, стабильные
   идентификаторы событий и структурированный журнал. Это текущий этап.
3. Добавить подписанный manifest конкретной сборки игры: размеры, SHA-256
   файлов и нормализованных PE-секций, разрешённые publishers/модули.
4. Реализовать PE-aware integrity: проверять executable-секции блоками,
   учитывать relocations/imports и сообщать точный RVA изменившегося блока.
5. Коррелировать loader list с регионами `MEM_IMAGE`; отдельно оценивать
   executable `MEM_PRIVATE`, RWX, PE-заголовки вне известных image ranges и
   смену защиты страницы во времени.
6. Добавить безопасную телеметрию потоков и debugger-сигналы как слабые
   признаки. Не опираться на недокументированные API без адаптера, проверки
   версии и fail-open поведения.
7. Ввести score с затуханием и дедупликацией. Например, неизвестный модуль —
   низкий сигнал; executable private region — средний; несовпадение подписанного
   code block плюс поток, исполняющийся в нём, — сильная корреляция.
8. Сначала выпускать новые правила в audit mode. Реакции разделить на
   telemetry, ограничение рейтинговой сессии, graceful disconnect и только
   затем санкции на сервере с возможностью апелляции.

## Уже реализовано

- ожидание процесса по имени через Toolhelp snapshot;
- открытие с минимальными правами только для чтения;
- получение полного пути executable и удержание handle до выхода процесса;
- перечисление x64/x86-модулей с повторами при `ERROR_BAD_LENGTH`;
- сигнал для модулей вне каталогов игры и Windows (`signal_only`);
- обход виртуальной памяти и сигнал для executable private/RWX regions вне
  известных модулей;
- JSONL-события с UTC timestamp, PID, scan ID и severity;
- корректное завершение по Ctrl+C и при выходе игры;
- unit-тесты границ путей, диапазонов модулей и JSON escaping.

Каталог сам по себе не является доверием. Текущая проверка расположения —
только начальная эвристика до появления подписанного manifest.

## Сборка

Нужны Windows 10/11, Visual Studio 2022 с workload «Desktop development with
C++» и CMake 3.24+.

```powershell
cmake -S . -B build -A x64
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure
```

Запуск одного сканирования:

```powershell
.\build\Release\anticheat.exe --process game.exe --once
```

Постоянный мониторинг раз в пять секунд:

```powershell
.\build\Release\anticheat.exe `
  --process game.exe `
  --interval-ms 5000 `
  --log anticheat-events.jsonl
```

Пример события:

```json
{"timestamp":"2026-07-28T10:00:00.000Z","severity":"medium","event":"suspicious_executable_region","pid":1234,"details":{"scan_id":1,"base":"0x12340000","size":4096,"protect":64,"type":"private","outside_known_module":true,"reason":"executable_non_image_memory","verdict":"signal_only"}}
```

## Текущие ограничения

- проект должен быть собран и проверен на Windows; на macOS CMake завершится с
  понятной ошибкой;
- при нескольких процессах с одинаковым именем выбирается первый найденный;
- нет manifest, Authenticode и PE-aware integrity;
- нет дедупликации одинаковых сигналов между scan ID;
- JIT/скриптовые runtime могут легитимно создавать executable private memory;
- лог пока не ротируется и не защищён от локальной подмены;
- реализация намеренно не содержит автоматического бана или завершения игры.
